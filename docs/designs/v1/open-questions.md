# 还没定的事

每条给一个建议的默认。拍板后把结论写进对应的设计文档，从这里删掉。

## 1. 怎么标记「公开」

**建议**：博文 frontmatter 加 `publish: bool`，默认 `false`。

备选：一个 `公开/` 目录（但目录已经用来表达系列了，会冲突）；一份单独的发布清单文件（多一处要同步）。

## 2. 草稿怎么表达

**建议**：不加状态字段。没写完的博文照样是博文，只是 `publish: false`。如果想在时间线里区分，再加 `draft: bool`。

备选：`草稿/` 目录（同样和系列冲突）；一个用户层 `draft`。

## 3. 条目发不发

**建议**：v1 不发。条目引用的博文不一定都公开，发出去会断链或泄露。等有了需求再设计「只发出处全部公开的条目」。

## 4. 回看靠什么触发

**建议**：v1 只做被动的——前端和 CLI 能列出「最久没回看的博文」（从 git log 里算最后一篇后记的日期）。不做提醒、不做间隔重复。

备选：按间隔重复（1 周 / 1 月 / 3 月）提醒；每次打开随机推一篇旧文。

## 5. AI 参与到什么程度

素材里很多是和 AI 的对话。AI 能帮什么、不能帮什么：

**建议**：v1 不内置 AI。可以以后考虑两件小事：从一段对话素材里**提问**（「你当时为什么选了这个方向？」）帮人开始写；在写 insight 时**找出**说同一件事的几篇博文。不让 AI 代写博文正文。

## 6. 用户直接改 `metas/` 里的文件

服务进程是唯一写者，但文件就在磁盘上，用户难免用编辑器直接改。

**建议**：v1 服务启动和每次写之前检查工作区，有未提交的改动就报错并给出 `metablog meta adopt`（把改动按层校验后补成提交）的提示。不静默覆盖。

## 7. 内容放哪

**已定（可改）**：代码在仓库里，内容在 `~/.metablog/metas/`，和 memory.talk 一样分开。如果更想要 Hexo / Hugo 那样「内容就在仓库里」，把 `metas/` 挪进仓库根即可，层机制不变。

## 8. `kind` 的取值

**已定（可改）**：复盘 / 觉察 / 方法 / 提问，含义见 [product.md](product.md#元认知指什么)。用了一阵如果发现总有文章不知道归哪类，再调。
